# Deploying Meal Hacker

The site runs as two services:

- **Backend:** the Django API on **Render**, with a free Postgres database.
- **Frontend:** the Next.js site on **Vercel**.

Vercel forwards `/api/*` to Render, so the browser only ever talks to the Vercel address.

Work through this list from top to bottom. Each box is something to tick off.

---

## 0. The night before: run the final sweep

```bash
scripts/final-sweep.sh
```

It runs every automated check and writes `sweep-reports/<timestamp>/REPORT.md`. It takes 10–20 minutes, so you can start it and walk away. It never pushes or deploys anything.

- **Checks:** secret scan, Django checks and tests, the production-settings deploy check, lint, typecheck, unit tests, the production build, dependency audits, the end-to-end and accessibility tests, and Lighthouse.
- **Faster options:**
  - `scripts/final-sweep.sh --quick` skips the end-to-end tests and Lighthouse, and takes about 5 minutes.
  - `--no-lighthouse` skips only Lighthouse.

- [ ] `REPORT.md` says **no failures**
- [ ] Every **WARN** row has been read. Each one is either fixed or deliberately accepted (see "Known warnings" at the bottom).
- [ ] The GitHub Actions run on the PR is green (backend, frontend and e2e)

## 1. Code and repo

- [ ] The `redesign` PR is merged into `main`
- [ ] `git ls-files | grep -E '(^|/)\.env$'` prints nothing, so no real `.env` is committed
- [ ] You have your Spoonacular and Groq API keys ready. They go only into the Render dashboard, never into git.
- [ ] **Code change to make before going live:** set `NUM_PROXIES` for the Vercel → Render setup. Without it, the per-visitor rate limits on login and the assistant can be bypassed by calling Render directly. Ask Claude to add it as an environment-configurable setting.

## 2. Backend on Render

1. In Render, go to **New → Blueprint** and pick the `marianealidio/meal-hacker` repo. It reads `render.yaml` and creates:
   - **meal-hacker-api**, a Python web service with root `backend/`;
   - **meal-hacker-db**, a free Postgres database.
2. When Render asks for the variables marked `sync: false`, fill them in:

| Variable | Value |
|---|---|
| `SPOONACULAR_API_KEY` | your Spoonacular key. Leave it blank for offline sample recipes. |
| `GROQ_API_KEY` | your Groq key. Leave it blank for a canned assistant reply. |
| `ALLOWED_HOSTS` | `meal-hacker-api.onrender.com` (the Render hostname, which is also added automatically) |
| `CSRF_TRUSTED_ORIGINS` | your Vercel address, e.g. `https://meal-hacker.vercel.app`. Add any custom domain too, comma-separated. |

`SECRET_KEY` is generated by Render, and `DATABASE_URL` comes from the database.

- [ ] The first deploy finishes. The build runs `migrate` and `seed_demo`, so look for "Demo kitchen ready." in the build log.
- [ ] `https://<render-host>/api/health/` returns `{"status":"ok"}`
- [ ] `https://<render-host>/api/does-not-exist/` returns a JSON 404 (`{"error": …}`), not an HTML page
- [ ] `https://<render-host>/admin/` shows the Django admin login with styling. If it's unstyled, static files didn't collect.
- [ ] Optional: create an admin user from Render's **Shell**: `python manage.py createsuperuser`

> Free Render services go to sleep after about 15 minutes idle, and the first request then takes 30–60 seconds. The site shows "The kitchen is waking up…" while that happens. Free Postgres databases expire after a fixed period, so check Render's current limit and set a reminder.

## 3. Frontend on Vercel

1. In Vercel, go to **Add New → Project**, import the repo, and set **Root Directory** to `frontend`. The framework is detected as Next.js.
2. Add this environment variable for both **Production** and **Preview**:

| Variable | Value |
|---|---|
| `BACKEND_URL` | `https://<render-host>`, with no trailing slash |

3. Deploy.

- [ ] The build succeeds
- [ ] If the Vercel address differs from what you put in `CSRF_TRUSTED_ORIGINS`, update it on Render and redeploy the backend
- [ ] To test preview deploys too, add their origin, e.g. `https://meal-hacker-git-redesign-<you>.vercel.app`, to `CSRF_TRUSTED_ORIGINS`. Origins must match exactly; wildcards don't work.

## 4. Smoke test the live site

Do this in a private window, first on desktop and then on your phone.

- [ ] The landing page loads, with photos, the wave dividers, and no sideways scrolling on the phone
- [ ] **Open the kitchen** goes to the dashboard. If it shows "waking up", wait 30 seconds and try again.
- [ ] Dashboard: Tonight's pick has a photo, description and chips. Expiring soon and This week are filled in.
- [ ] Kitchen: quick-add "2 lemons" adds a card. Mark as used removes it.
- [ ] Recipes: search "soup" works. Open a recipe, then use **Add to plan**. A toast confirms and the meal shows on the Planner.
- [ ] Shopping: tick an item, then use **Move to kitchen** from the toast. It appears in Kitchen.
- [ ] The assistant panel answers a question. With no Groq key, it gives the offline reply.
- [ ] Log out from the sidebar (desktop) or the avatar menu (phone). You land back on the landing page.
- [ ] Sign up a fresh account, go through onboarding, and check that the dashboard has suggestions.
- [ ] Log in with that account in a second browser. Change the diet on the Profile page and check that suggestions change.
- [ ] Visit `/does-not-exist` and check that the "This shelf is empty" page shows
- [ ] The browser console shows no errors on the main pages

## 5. After launch

- [ ] Run Lighthouse on the live landing page (Chrome DevTools → Lighthouse). Aim for 90+ in every category.
- [ ] Add the live link to the README and to your CV or portfolio
- [ ] Check Spoonacular's daily quota after a day of visitors. The recipe cache keeps searches for 24 hours and recipe details for 7 days.
- [ ] Optional: add a custom domain in Vercel, then add it to `CSRF_TRUSTED_ORIGINS` on Render

## Rolling back

- **Frontend:** Vercel → Deployments, then **Promote** the previous deployment.
- **Backend:** Render → the service → Deploys, then **Rollback** to the previous deploy.
- **Demo kitchen gone strange:** run `python manage.py seed_demo --reset` from Render's Shell.

## Known warnings

These may show up as WARN in the sweep report. They are not blockers:

- **Django deploy check:**
  - About 20 `drf_spectacular.W002` lines say the API schema generator can't describe some function views. They only affect the auto-generated API docs, not the site.
  - The real items are `SECURE_SSL_REDIRECT` (Render already redirects to HTTPS, but turning it on is cheap) and the HSTS options. Leave `SECURE_HSTS_SECONDS` at 0 until the site has been stable on HTTPS, then set it, e.g. `31536000`. Only add `SECURE_HSTS_INCLUDE_SUBDOMAINS`/`PRELOAD` with a custom domain you fully control.
- **npm audit (postcss, high):** the flagged copy of PostCSS is bundled inside Next.js 15 and only runs at build time on our own CSS, so visitors can't exploit it. The only fix is upgrading to Next.js 16, which is a breaking change. Accepted for now.
- **Lighthouse landing performance in the 80s locally:** the hero photo goes through local image optimisation on a cold start, which pushes "largest contentful paint" to about 4s. Re-check on the deployed URL; Vercel's image cache makes it faster.
- **Working tree not clean:** the sweep tests what's on disk, including uncommitted changes. Commit first if you want the report to match the PR exactly.
